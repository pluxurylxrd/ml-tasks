# Задача 1. Анализ тональности отзывов на товары

## ТЗ

Определять эмоциональную окраску отзывов покупателей маркетплейса
на русском языке: negative / neutral / positive

Вход - текст отзыва, не более 512 токенов
Выход - метка класса и вероятности по всем трём классам

## Преимущества выбранной библиотеки (Hugging Face Transformers)

- единый интерфейс к тысячам готовых моделей, смена модели - одна строка
- автоматическая загрузка и кэширование весов, повторный запуск не требует сети
- токенизатор поставляется вместе с моделью, не нужно угадывать предобработку
- названия классов хранятся в конфиге модели (id2label) и не хардкодятся в коде

## Принцип работы модели и причины её выбора

Модель: cointegrated/rubert-tiny-sentiment-balanced

Архитектура - BERT, двунаправленный трансформер. Модель читает отзыв целиком
и для каждого токена строит вектор с учётом всего контекста слева и справа.
Вектор служебного токена подаётся в линейный классификатор на три выхода,
результат нормализуется softmax в вероятности классов

Причины выбора:
- rubert-tiny - уменьшенная версия BERT для русского языка, веса 47 МБ против
  примерно 700 МБ у полноразмерного ruBERT
- вариант balanced дообучен на сбалансированной выборке и не завален в сторону
  самого частого класса
- малый размер критичен: в части 2 модель загружается при каждом автоматическом
  прогоне тестов в GitHub Actions

## Структура датасета

Модель дообучена на корпусах русскоязычных отзывов, собранных Сметаниным
(отзывы на товары, банки и рестораны, посты из социальных сетей)
Разметка - три класса: negative, neutral, positive

Для оценки работоспособности решения составлена собственная синтетическая
выборка из 36 отзывов о товарах маркетплейса: data/test_samples.json
Формат - список объектов с полями text и label, по 12 примеров на класс

Ограничение: выборка синтетическая и небольшая, в неё намеренно включены
сложные случаи (отрицания, сарказм, пограничные формулировки). Полученные
метрики показывают работоспособность решения и характер ошибок модели,
но не являются оценкой её качества на реальном потоке отзывов

## Метрики оценки качества

Задача - многоклассовая классификация, поэтому используются:
- Accuracy - общая доля верных ответов
- Precision / Recall / F1 по каждому классу - показывают, на каком классе
  модель ошибается, чего accuracy не отражает
- macro avg - среднее по классам без учёта их размера
- матрица ошибок - в какую сторону происходит путаница

## Анализ ошибок

Модель корректно сопоставляет классы: по диагонали матрицы везде максимум
Выявлены три типа ошибок

1. Негатив определяется как нейтральный (4 случая). Модель не распознаёт
   претензию, поданную без эмоционально окрашенных слов, и сарказм.
   Пример: «Проработало ровно до конца гарантии и сдохло. Совпадение?»

2. Позитив определяется как негатив (4 случая). Основная причина - отрицания,
   переворачивающие смысл в конце предложения.
   Пример: «Сомневалась из-за цены, но зря»

3. Нейтральные отзывы уходят в позитив (3 случая). Констатация соответствия
   товара описанию воспринимается как одобрение. Ошибка наименее критичная

Вывод: rubert-tiny из-за малого числа слоёв слабо улавливает отрицание
и подтекст. Для промышленной эксплуатации требуется модель большего размера
либо дообучение на доменных данных маркетплейса

## Особенности реализации и эффективность

- ленивая загрузка: модель читается один раз и переиспользуется при всех
  последующих вызовах
- torch.no_grad() - градиенты не вычисляются, снижается расход памяти
  и время инференса
- model.eval() - отключены dropout и прочая случайность, вывод детерминирован
- truncation до 512 токенов - защита от падения на длинных отзывах
- валидация пустого ввода с выбрасыванием ValueError
- названия классов берутся из model.config.id2label

Замеры (CPU):
- загрузка модели: 1.50 с
- предсказание 36 отзывов: 0.37 с
- в среднем на отзыв: 10.2 мс

Загрузка модели на два порядка дороже одного предсказания, поэтому
в API (часть 2) модель загружается однократно при старте приложения,
а не на каждый запрос
